# Image delivery — runbook

Public photos (avatars, store logos/covers, menu items, banners, food categories, ride vehicle
classes) are served as WebP at display widths, then cached on the device and at the CDN edge.
`ObjectStorage` (Cloudflare R2) holds the bytes; the API only proxies what a client asks for.

## Pipeline

1. **Upload** (`DocumentStoreService.storePublicThen`): re-encode to WebP with `sharp`, write the
   base object, then one variant per `PUBLIC_IMAGE_VARIANT_WIDTHS = [128, 240, 480, 1080]`.
   An unreadable image is stored untouched instead of being lost.
2. **Read** (`DocumentStoreService.readDisplayImage`): `?w=` is snapped up to the smallest covering
   variant (`resolveImageVariantWidth`), the variant object is fetched, and the original is the
   fallback for uploads made before variants existed.
3. **Client** (`mobile/lib/core/design_system/components/dealgo_network_image.dart`): the widget
   measures its box, computes `decodeWidth = max(w, 2h) * dpr`, asks
   `withImageWidth()` for the matching bucket and decodes at that size. Bytes are kept on disk by
   `DealGoImageCache` (`flutter_cache_manager`, 30-day stale period, 300 objects) and in memory by
   Flutter's `ImageCache`.

## Object layout

| Image | Key |
|---|---|
| Menu item | `menu-items/<itemId>/<uuid>.w480.webp` |
| Avatar | `avatars/<userId>/<uuid>.w240.webp` |
| Store logo / cover | `store-logos/<storeId>/<uuid>.webp`, `store-covers/...` |
| Banner | `home-banners/images/<bannerId>/<uuid>.w1080.webp` |
| Food category | `food-categories/images/<code>/<uuid>.webp` |
| Ride vehicle class | `ride-vehicle-classes/<CODE>/<uuid>.webp` |

Keys are random per upload, so a key is immutable: changing a photo writes a new key and the old
objects are removed by the upload-reference cleanup worker (`backend/src/workers/upload-references.ts`,
which also protects `.w<width>.webp` siblings from orphan deletion).

## Caching

| Layer | Behaviour |
|---|---|
| HTTP | `cache-control: public, max-age=31536000, immutable` on every public image controller. |
| Cloudflare | Caches the API image responses per URL (including `?w=`); a miss costs one origin round trip, then `cf-cache-status: HIT`. |
| API process | `readDisplayImage` keeps up to 96 MB / 600 entries (≤ 4 MB each) in an LRU, so repeated views skip R2. Entries are dropped when the object is discarded. |
| Flutter disk | `DealGoImageCache` persists bytes across launches; a cold app does not re-download photos it already showed. |

## Backfill (images uploaded before variants existed)

```bash
cd backend
npx tsx prisma/backfill-image-variants.ts                      # report only
IMAGE_BACKFILL_APPLY=1 npx tsx prisma/backfill-image-variants.ts  # write
```

Rewrites `users.avatarUrl`, `food_stores.logoUrl/coverUrl`, `food_items.imageUrl/imageUrls`,
`ride_vehicle_classes.imageUrl`, `food_categories.imageUrl`, `home_banners.imageUrl` and
`food_order_lines.imageUrl` to the `.webp` object. Old objects are left in place and cleaned by the
orphan worker.

Demo/showcase data is regenerated by `npx tsx prisma/seed-dev-showcase.ts` (dev-only guard), which
uploads WebP plus variants and skips any object already present.

## Verify

```bash
BASE=https://api-dealgo.laptrinhapp.com
IMG=/v1/public/menu-items/<itemId>/<uuid>.webp

for w in 128 240 480 1080; do
  curl -s -o /dev/null -D - "$BASE$IMG?w=$w" | grep -iE 'content-type|content-length|cache-control|cf-cache-status'
done
```

Expect `content-type: image/webp`, a payload growing with `w`, `cache-control: …immutable`, and
`cf-cache-status: HIT` on the second call. Origin latency on a CDN miss is measured with
`curl -w '%{time_starttransfer}' http://127.0.0.1:3001$IMG?w=240` on the VPS: ~300 ms for the first
read from R2 and ~5 ms once the in-process cache holds the bytes.

## Limits / next steps

- R2 sits behind `https://<account>.us.r2.cloudflarestorage.com`; a cold read costs a TLS handshake
  plus a trans-Pacific round trip. Uploading through a custom domain bound to the bucket would let
  Cloudflare cache object bytes without the API in the path.
- Cloudflare fills its cache per edge location and per exact `?w=` value; clients must send the
  buckets (they do), otherwise each arbitrary width becomes its own edge entry.
